# 第三阶段：核心流程（Core Flow）

## 一、复述理解

- **目标**：搞懂"你发一条消息 → 收到流式回复"背后，请求在 DeerFlow 内部走过的完整链路。
- **范围**：HTTP 入口 → 服务层 `start_run` → 后台 `run_agent` → `make_lead_agent` 编排图 → `StreamBridge` 推 SSE。
- **步骤**：
  1. 画出一条消息的端到端调用时序图
  2. 逐段拆解每个环节的职责与关键代码
  3. 解释主 Agent 的 middleware（中间件）链
  4. 给出调试抓手（日志、事件、token 统计）

## 三、逐段拆解（带行号，可直接对照源码）

### ① HTTP 入口：两种 run
- **有状态**：`POST /api/threads/{thread_id}/runs/stream` — `thread_runs.py:124`
- **无状态**：`POST /api/runs/stream` — `runs.py:35`（自动建临时 thread；若 body 带 `thread_id` 就复用历史）

两者都调用同一个 `start_run()`，保证行为一致。前端 `useStream` React hook 用的就是这套 LangGraph 兼容协议（`runs.py:8` 注释说明）。

### ② 服务层 `start_run`（services.py:248）
关键三步：
1. **并发控制**：`run_mgr.create_or_reject(...)`，依据 `multitask_strategy`（reject/rollback/interrupt/enqueue）决定同线程并发时怎么办（`services.py:289`）。
2. **配置组装**：`build_run_config()` 把 `thread_id`、`agent_name`（自定义 Agent）写进 `config.configurable`（`services.py:172`）。`assistant_id` 非 `lead_agent` 时会被规范化为 `agent_name` 注入（`services.py:226`）。
3. **异步派发**：`asyncio.create_task(run_agent(...))`（`services.py:332`）—— 注意这里**立刻返回** `RunRecord`，不阻塞 HTTP 请求；流式结果走 SSE。

### ③ 后台执行 `run_agent`（worker.py:120）
- 把 `thread_id`/`run_id`/`app_config` 塞进 `Runtime.context`，让工具和 middleware 能拿到（`worker.py:217`）。
- `agent = agent_factory(config)` 即 `make_lead_agent`（`worker.py:229`）。
- 绑定 checkpointer（状态持久化）和 store（`worker.py:246`）。
- 核心循环：`agent.astream(graph_input, config, stream_mode=...)`，每产出一块就 `bridge.publish(...)`（`worker.py:286`）。
- `recursion_limit` 默认 **100**（`services.py:193`），防止无限递归。

### ④ 主 Agent 图 `make_lead_agent`（agent.py:343）
这是 DeerFlow 的"心脏"。它不是手写 `StateGraph`，而是用 LangChain 的 `create_agent` + 一堆 **middleware（中间件）** 声明式构建（agent.py:434）：

```python
create_agent(
    model=create_chat_model(name=model_name, thinking_enabled=..., ...),
    tools=filter_tools_by_skill_allowed_tools(tools + extra_tools, ...),
    middleware=_build_middlewares(...),
    system_prompt=apply_prompt_template(...),
    state_schema=ThreadState,
)
```

- **state_schema=ThreadState**：图的全局状态就是 `ThreadState`（消息列表等都存在这里）。
- **tools**：来自 `get_available_tools()`（受 `tool_groups`、`subagent_enabled` 过滤），外加 `update_agent`（自定义 Agent 才能改自己 SOUL）。
- **middleware**：见下一节。

## 四、Middleware 链：DeerFlow 的"隐形工作流"

`_build_middlewares()`（agent.py:240）按固定顺序串起一串中间件，每次 LLM 调用前后都会穿过它们：

| 顺序 | Middleware | 作用（英文 → 中文） |
|------|-----------|---------------------|
| 1 | `DynamicContextMiddleware` | 注入当前日期/记忆提示，保持 system prompt 静态利于缓存 |
| 2 | `DeerFlowSummarizationMiddleware` | 上下文过长时自动摘要压缩（配置见 `config.yaml` summarization） |
| 3 | `TodoMiddleware` | 仅 plan 模式启用，管理 `write_todos` 任务清单 |
| 4 | `TokenUsageMiddleware` | token 用量统计（`config.yaml` token_usage） |
| 5 | `TitleMiddleware` | 首轮后自动生成对话标题 |
| 6 | `MemoryMiddleware` | 把对话沉淀进长期记忆（`config.yaml` memory） |
| 7 | `ViewImageMiddleware` | 模型支持视觉时注入图片细节 |
| 8 | `SubagentLimitMiddleware` | 限制并行子 Agent 数量（subagent 开启时） |
| 9 | `LoopDetectionMiddleware` | 检测并打断重复工具调用死循环 |
| 10 | `ClarificationMiddleware` | 最后兜底：信息不足时向用户澄清 |

> 这些中间件让你"不改核心代码"就能获得摘要、记忆、标题、防死循环等企业级能力——这正是 DeerFlow 比裸 LangGraph 好用的地方。

## 五、子 Agent 是如何"长出来"的

- 主图是否带"派生子 Agent"的工具，由 `config` 里的 `subagent_enabled` 决定（`agent.py:362`）。
- 开启后：`get_available_tools(..., subagent_enabled=True)` 会纳入 `task` 类工具，`SubagentLimitMiddleware` 限制并发（`agent.py:302`）。
- 每个子 Agent 也是用同样的 `make_lead_agent` 工厂造出来的独立图，拥有自己的隔离上下文（README 称 "Isolated Sub-Agent Context"），跑完把结构化结果回传主 Agent 汇总。
- 详情留到 **第五阶段：多智能体编排** 展开。

## 六、调试抓手（你排错时很有用）

1. **看 SSE 原始流**：浏览器 DevTools → Network → 过滤 `runs/stream` → 看 `event:` 帧（`metadata` / `messages-tuple` / `values` / `end`）。
2. **看后端日志**：`make docker-logs-gateway`。每次 run 都会打印 `Create Agent(...) -> model_name ...`（`agent.py:383`）和 `streaming with modes ...`（`worker.py:280`）。
3. **事件审计**：`GET /api/threads/{tid}/runs/{rid}/events`（`thread_runs.py:377`）拿完整事件链。
4. **Token 统计**：`GET /api/threads/{tid}/token-usage`（`thread_runs.py:392`），按模型/调用方（lead/subagent/middleware）聚合。
5. **状态查询**：`GET /api/threads/{tid}/runs/{rid}` 看 run 状态（`pending/running/success/error/timeout/interrupted`，见 `schemas.py:6`）。

## 七、常见坑（Pitfalls）

1. **`model_name` 不在白名单** → 直接 400。`start_run` 会校验（`services.py:279`），所以 `context.model_name` 必须是 `config.yaml` 里真实存在的 name。
2. **以为 HTTP 接口会等推理完成** → 不会。`start_run` 立即返回，结果走 SSE；想阻塞等结果用 `POST .../runs/wait`（`thread_runs.py:152`）。
3. **同线程狂点发送** → 受 `multitask_strategy` 约束，默认 `reject` 会 409 冲突（`services.py:298`）。
4. **`events` stream_mode 被静默忽略** → gateway 不支持 `events` 模式（`worker.py:155`），只能用 `values`/`messages-tuple`/`updates`。
5. **改了 System Prompt 不生效** → 确认是改了 `lead_agent/prompt.py` 的模板，且 `ThreadState` 真的被作为 `state_schema` 传入（agent.py:445）。
6. **子 Agent 没出现** → 检查 `context.subagent_enabled` 是否为 true，或 `config.yaml` 的 `subagents` 段是否被启用。

## 八、本阶段小结

- 一条消息的完整路径：**Router → `start_run`（建单+异步派发）→ `run_agent`（后台执行）→ `make_lead_agent`（构图）→ `astream` 产出 → `StreamBridge` → SSE → 浏览器**。
- HTTP 层与执行层解耦：`start_run` 立刻返回，`run_agent` 在 `asyncio.Task` 里跑。
- 主 Agent = `create_agent(model, tools, middleware, prompt, ThreadState)`，能力几乎全由 **middleware 链** 提供。
- 排错优先看 gateway 日志 + SSE 帧 + token-usage 接口。
