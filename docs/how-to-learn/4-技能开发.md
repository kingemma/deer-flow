## 二、Skill 的本质：一份带 frontmatter 的 Markdown

一个 Skill 就是**一个目录 + 一个 `SKILL.md` 文件**。核心数据结构：

```19:31:backend/packages/harness/deerflow/skills/types.py
@dataclass
class Skill:
    """Represents a skill with its metadata and file path"""
    name: str
    description: str
    license: str | None
    skill_dir: Path
    skill_file: Path
    relative_path: Path  # Relative path from category root to skill directory
    category: SkillCategory  # 'public' or 'custom'
    allowed_tools: list[str] | None = None
    enabled: bool = False  # Whether this skill is enabled
```

### `SKILL.md` 的 frontmatter 规范
由 `parser.py` 用正则抽取 `---` 之间的 YAML，`validation.py` 规定**允许的属性**与**命名规则**：

```15:15:backend/packages/harness/deerflow/skills/validation.py
ALLOWED_FRONTMATTER_PROPERTIES = {"name", "description", "license", "allowed-tools", "metadata", "compatibility", "version", "author"}
```

校验规则（关键约束，违反会直接判定无效）：
- `name` / `description` **必填**，且非空白字符串。
- `name` 必须是 **hyphen-case**：仅小写字母、数字、连字符，且不能 `.startswith("-") / endswith("-") / "--"`、长度 ≤ 64（`validation.py:70-75`）。
- `description` 不能含 `<` `>`、长度 ≤ 1024（`validation.py:82-86`）。
- `allowed-tools` 可选，必须是字符串列表（可为空列表）。

> 这就是 Skill 的全部"编译契约"：一份 Markdown + 合规 frontmatter。没有 Python 代码也能成为一个 Skill（纯知识型）；也可以 `allowed-tools` 列出工具名，让主 Agent 在启用该 Skill 时**只允许调用这些工具**。

## 三、Skill 存在哪里、怎么被发现

### 存储布局（来自 `local_skill_storage.py`）
```
<skills_root>/public/<name>/SKILL.md     # 平台内置，只读
<skills_root>/custom/<name>/SKILL.md     # 用户自定义，可编辑/删除
<skills_root>/custom/.history/<name>.jsonl  # 编辑历史（支持回滚）
```
README 明确：宿主路径 `deer-flow/skills/` 挂载到容器 `/mnt/skills`（`README.md:74-75`）。

### 递归发现
`LocalSkillStorage._iter_skill_files` 会 `os.walk` 整个 `skills/{public,custom}`，只要目录里含 `SKILL.md` 就被视作一个 Skill，**支持嵌套子目录**（保留相对容器路径，`local_skill_storage.py:63-74`）。

### 解析流程
`parse_skill_file`（`parser.py:35`）：
1. 必须是 `SKILL.md` 且存在；
2. 正则抽取 `^---\n(.*?)\n---\n` 的 frontmatter；
3. `yaml.safe_load` 解析；
4. 校验 `name`/`description` 非空字符串；
5. `parse_allowed_tools` 解析白名单（`parser.py:12`）。

## 四、Skill 如何"进入"主 Agent（双通道）

这是本阶段最关键的部分。一个启用的 Skill 会从**两个通道**影响主 Agent：

### 通道 A：知识注入（写进 system prompt）
`prompt.py` 在构建 system prompt 时，从缓存读取所有**已启用**的 Skill，并渲染成 `{skills_section}` 拼进模板（`prompt.py:29` / `prompt.py:799` / `prompt.py:813-823`）。

system prompt 里还有一条强制指令强调它的优先级：

```542:542:backend/packages/harness/deerflow/agents/lead_agent/prompt.py
- Skill First: Always load the relevant skill before starting **complex** tasks.
```

> 意味着：LLM 实际"看到"的是 SKILL.md 的**正文内容**（指引/步骤/注意事项），它据此调整自己的行为。Skill 正文不会被自动执行代码，而是作为"最佳实践知识"被模型采纳。

### 通道 B：工具白名单（限制可调用工具）
主 Agent 在 `agent.py` 组装 `tools` 时，会用 `filter_tools_by_skill_allowed_tools` 过滤：

```436:436:backend/packages/harness/deerflow/agents/lead_agent/agent.py
        tools=filter_tools_by_skill_allowed_tools(tools + extra_tools, skills_for_tool_policy),
```

过滤逻辑非常讲究（`tool_policy.py`）：

```39:44:backend/packages/harness/deerflow/skills/tool_policy.py
def filter_tools_by_skill_allowed_tools[ToolT: NamedTool](tools: list[ToolT], skills: list[Skill]) -> list[ToolT]:
    allowed = allowed_tool_names_for_skills(skills)
    if allowed is None:
        return tools

    return [tool for tool in tools if tool.name in allowed]
```

关键语义（`allowed_tool_names_for_skills`，`tool_policy.py:13`）：
- 如果**没有任何** Skill 声明 `allowed-tools` → 返回 `None` → **全部工具放行**（legacy 行为）。
- 一旦**有任意一个** Skill 声明了 `allowed-tools` → 取所有声明 Skill 的**工具并集**作为白名单；未声明该字段的旧 Skill **不再贡献任何工具**（避免错误地解除限制）。
- 空列表 = 该 Skill 明确"不需要任何工具"。

> 设计意图：你是平台管理员时，可以用 `allowed-tools` 做到"启用这个 Skill 时，主 Agent 只能调这几样工具"，实现权限最小化。

`skills_for_tool_policy` 来自 `_load_enabled_skills_for_tool_policy`，它还会被 `agent_config.skills`（自定义 Agent 的技能范围）再过滤一次（`agent.py:329-340`、`agent.py:321-326`）：

```338:340:backend/packages/harness/deerflow/agents\lead_agent\agent.py
    if available_skills is None:
        return skills
    return [skill for skill in skills if skill.name in available_skills]
```

## 五、动手：创建一个你自己的 Skill

### 步骤 1：建目录与文件
在 `deer-flow/skills/custom/` 下创建：
```
deer-flow/skills/custom/weather-tips/SKILL.md
```

### 步骤 2：写 `SKILL.md`（可照抄此模板）
```markdown
---
name: weather-tips
description: 当用户询问出行/穿衣/天气相关建议时使用本技能，提供结构化建议模板。
license: MIT
allowed-tools: []
---

# 天气建议技能

## 适用场景
- 用户问"明天去北京穿什么"
- 用户问"周末适合出游吗"

## 工作流程
1. 先用 `search` 类工具获取目的地的天气。
2. 按"温度区间 → 穿衣建议 → 注意事项"三段式输出。
3. 若涉及雨雪，必须提醒带伞/防滑。

## 注意事项
- 不要编造没有数据支撑的预报。
- 给出建议时始终标注信息来源日期。
```

> 说明：`allowed-tools: []` 表示这是一个**纯知识型 Skill**，不额外开放任何工具（主 Agent 仍保持原有基础工具）。若想让该 Skill 专属启用某工具，可写成 `allowed-tools: [web_search, read_file]`。

Skill 默认 `enabled: False`。启用状态由 **`extensions_config.json`** 里的 `skillStates` 控制（见 `skills.py` 路由：`SkillStateConfig`、`get_extensions_config`）。最简做法：通过 API 或 UI 将 `weather-tips` 置为 `enabled: true`。

除了手写文件，Skill 还支持打包成 `.skill`（本质是 zip）后通过 API 安装：

    """Request model for installing a skill from a .skill file."""

安装流程（`local_skill_storage.py:94-155`，`ainstall_skill_from_archive`）：
1. 校验扩展名必须是 `.skill`；

3. `_validate_skill_frontmatter` 再次校验合规；

5. 复制到 `custom/<skill_name>/`，并做"暂存 → 原子移动"防止半写入。

> 这套安装链路还集成了 `security_scanner.py`（内容安全扫描），所以生产环境分发 Skill 走 `.skill` 归档比直接放文件更规范、更安全。

## 八、常见坑（Pitfalls）

1. **写完 Skill 没启用** → 默认 `enabled=False`，主 Agent 完全看不到。✅ 必须在 `extensions_config.json` / API 置 `enabled: true`。
2. **`name` 用了驼峰或下划线** → `validation.py:70` 正则拒绝，判定无效 Skill。✅ 必须用 `hyphen-case`（如 `weather-tips`）。
3. **`description` 太长或含尖括号** → 校验失败。✅ 控制在 1024 字内、不含 `<>`。
4. **误以为 Skill 会自动执行代码** → 不会。Skill 正文只是注入 prompt 的"知识"，真正执行靠工具；想限制工具才用 `allowed-tools`。
5. **随意给旧 Skill 加 `allowed-tools` 破坏了全局放行** → 一旦任一 Skill 声明 `allowed-tools`，未声明的旧 Skill 工具会被**全部收回**（`tool_policy.py:13-36`）。✅ 要么所有 Skill 都声明，要么都不声明。
6. **把 Skill 放错目录** → 必须放在 `skills/public/` 或 `skills/custom/` 下且含 `SKILL.md`，否则 `os.walk` 扫不到。

## 九、本阶段小结

- DeerFlow 的 **Skill = `SKILL.md` 知识文档 + 可选工具白名单**，不是独立 Agent。
- 它被**双通道**接入主 Agent：① 正文注入 system prompt（"Skill First" 强制优先）；② `allowed-tools` 经 `filter_tools_by_skill_allowed_tools` 限制可调用工具。
- 存储布局 `skills/{public,custom}/<name>/SKILL.md`，递归发现，支持嵌套。
- 启用状态由 `extensions_config.json` 控制，后台线程异步刷新缓存，改完即时生效。
- 分发走 `.skill` 归档 + 安全扫描，生产更稳妥。
