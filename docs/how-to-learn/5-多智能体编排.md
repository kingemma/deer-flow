# 第五阶段：多智能体编排（Multi-Agent Orchestration）

## 一、复述理解

- **目标**：搞懂 DeerFlow 的"主 Agent 如何派生子 Agent、子 Agent 如何隔离运行、并发如何限制、配置如何编写"。
- **范围**：`task` 工具派发 → `SubagentExecutor` 执行器 → 隔离上下文 → `SubagentLimitMiddleware` 并发控制 → `config.yaml` 的 `subagents` 段（内置/自定义/覆盖）。
- **步骤**：
  1. 看清"多 Agent"的真相：主 Agent 调 `task` 工具
  2. 看子 Agent 的隔离执行模型
  3. 看并发与超时控制
  4. 在 `config.yaml` 定义一个自定义子 Agent
  5. 调试与常见坑

---

## 二、先澄清：DeerFlow 的"多 Agent"是什么

```
主 Agent (lead_agent)
   │  在推理中决定调用 task 工具
   ▼
task_tool(description, prompt, subagent_type)
   │  在后台起一个独立的 SubagentExecutor
   ▼
子 Agent (general-purpose / bash / 自定义)
   │  自己有独立的 create_agent 图 + 独立消息上下文
   │  但继承了父 Agent 的 sandbox_state / thread_data（可访问同一批文件）
   ▼
返回结构化结果 → 主 Agent 汇总
```

关键点：**子 Agent 不是主 Agent 里的一个节点，而是用同一套 `create_agent` 工厂单独造出来的"平行 Agent"**，运行在独立的事件循环里，跑完把结果回传。这就是 README 说的 "Isolated Sub-Agent Context（隔离子 Agent 上下文）"。

## 三、子 Agent 类型从哪来（注册表）

内置两种类型（`task_tool.py:151-162` 的 docstring 里也有说明）：
- **`general-purpose`**：通用复杂多步任务。
- **`bash`**：命令执行专家，仅在 host bash 允许 / 隔离沙箱时可用。

## 四、派发链路：`task_tool` 做了什么

`task_tool` 是主 Agent 唯一"生孩子"的入口。它做的事（`task_tool.py:136-265`）：

1. **校验类型**：`get_subagent_config(subagent_type)`，未知类型直接报错并列出可用类型（`task_tool.py:183-186`）。
2. **提取父上下文**：从 `runtime` 拿 `sandbox_state` / `thread_data` / `thread_id` / `parent_model` / `trace_id`（`task_tool.py:207-219`）——这就是"隔离但共享文件"的桥。
3. **技能白名单合并**：父的 `available_skills` 与子 Agent 配置的 `skills` 取交集（`_merge_skill_allowlists`，`task_tool.py:125-133` / `221-223`）。
4. **继承工具组但禁嵌套**：`get_available_tools(..., subagent_enabled=False)` —— **子 Agent 拿不到 `task` 工具，杜绝无限递归**（`task_tool.py:239-247`）。
5. **建执行器并后台跑**：`executor.execute_async(prompt, task_id=tool_call_id)`（`task_tool.py:265`）。
6. **轮询 + 流式上报**：每 5 秒查一次状态，通过 `get_stream_writer()` 把 `task_started` / `task_running` / `task_completed` 等事件推向 SSE（`task_tool.py:276-338`）。

> 注意 `task_running` 事件会把子 Agent 产生的每条 AI 消息实时回传前端，所以你在 UI 上能看到子 Agent "思考过程"逐步展开。

## 五、隔离执行模型（核心机制）

`SubagentExecutor`（`executor.py`）是真正的执行引擎：

### 5.1 独立的事件循环
子 Agent 不在父 Agent 的循环里跑，而是提交到一个**常驻的隔离事件循环**（daemon 线程），避免每次执行都新建/关闭 loop 导致共享 httpx 客户端失效（`executor.py:94-178`）。

### 5.2 独立上下文，共享沙箱
`_build_initial_state`（`executor.py:361-402`）给子 Agent 构造**全新的消息列表**（只有 system_prompt + 注入的 skill 消息 + 本次 task），并带入父的 `sandbox_state` / `thread_data`：

```392:402:backend/packages/harness/deerflow/subagents/executor.py
        state: dict[str, Any] = {
            "messages": messages,
        }

        # Pass through sandbox and thread data from parent
        if self.sandbox_state is not None:
            state["sandbox"] = self.sandbox_state
        if self.thread_data is not None:
            state["thread_data"] = self.thread_data

        return state, filtered_tools
```

> 这就是"隔离上下文"的含义：子 Agent 的对话历史**不污染**主 Agent，但它**能读写同一批沙箱文件**（因为共享 sandbox/thread_data）。

### 5.3 它自己也是个 Agent
`_create_agent`（`executor.py:277-297`）用 `create_agent` 造子图，复用主 Agent 的中间件组合 `build_subagent_runtime_middlewares`，但 `system_prompt=None`——因为 system prompt 已作为首条 `SystemMessage` 放进 messages 里（规避某些 LLM "多个 SystemMessage" 的限制，`executor.py:289-297`）。

### 5.4 取消是"协作式"的
无法强杀线程，所以靠 `cancel_event` 在 `astream` 每次迭代边界检测（`executor.py:471-484`）。父 Agent 被取消时，`task_tool` 调 `request_cancel_background_task` 设置该事件（`task_tool.py:357-358`）。

## 六、并发与超时控制

### 6.1 `SubagentLimitMiddleware`：限制单次"并行派发"数量
主 Agent 一次回复里可能想同时 `task` 多个子 Agent。中间件会把**超出上限的 `task` 调用直接截断丢弃**（比靠 prompt 限制更可靠）：

```37:39:backend/packages/harness/deerflow/agents/middlewares/subagent_limit_middleware.py
    def __init__(self, max_concurrent: int = MAX_CONCURRENT_SUBAGENTS):
        super().__init__()
        self.max_concurrent = _clamp_subagent_limit(max_concurrent)
```

上限被 **clamp 到 [2, 4]**，默认 3（`subagent_limit_middleware.py:16-22`）。被丢掉的调用会在日志里告警（`subagent_limit_middleware.py:60-64`）。

### 6.2 调度线程池 + 超时
- `_scheduler_pool = ThreadPoolExecutor(max_workers=3)`：后台子 Agent 调度池上限 3（`executor.py:89`）。
- 每个子 Agent 有 `timeout_seconds`（默认 900s），超时置 `TIMED_OUT` 并协作取消（`executor.py:728-737`）。
- `max_turns`（默认 50）作为 `recursion_limit` 防死循环（`executor.py:441-445`）。

## 七、子 Agent 的技能加载

子 Agent 也会按自己的 `skills` 白名单加载已启用 Skill，并**作为 `SystemMessage` 注入**（`<skill name="...">...</skill>` 包裹，`executor.py:330-359`）：

```350:354:backend/packages/harness/deerflow/subagents/executor.py
                content = await asyncio.to_thread(skill.skill_file.read_text, encoding="utf-8")
                content = content.strip()
                if content:
                    messages.append(SystemMessage(content=f'<skill name="{skill.name}">\n{content}\n</skill>'))
```

白名单语义（与主 Agent 一致）：
- `skills: None` → 继承所有已启用 Skill；
- `skills: []` → 不加载任何 Skill；
- `skills: ["a","b"]` → 仅加载 a、b。
（见 `subagents_config.py:28-31` 与 `executor.py:299-325`）

## 八、动手：在 `config.yaml` 定义自定义子 Agent

`subagents_config.py` 定义了配置结构。在 `config.yaml` 加一段 `subagents`：

```yaml
subagents:
  # 全局默认
  timeout_seconds: 900
  max_turns: 50
  # 每个内置/自定义 agent 的覆盖
  agents:
    general-purpose:
      timeout_seconds: 1200
      model: gpt-4o          # 让通用子 Agent 用更强模型
  # 自定义子 Agent 类型
  custom_agents:
    code-reviewer:
      description: 当用户需要审查代码、指出隐患时使用本子 Agent。
      system_prompt: |
        你是一名资深代码审查员。请关注：空指针、资源泄漏、
        并发安全、无明显测试覆盖的逻辑。给出结构化结论。
      tools: [read_file, bash]      # 白名单：只能读文件和执行命令
      disallowed_tools: [task, ask_clarification, present_files]
      model: inherit                 # 继承父 Agent 模型
      max_turns: 20
      timeout_seconds: 600
```

然后在对话里让主 Agent "审查这段代码"，它就会调用 `task(subagent_type="code-reviewer", ...)`。

配置解析顺序（`registry.py:50-116`，注释写得很清楚）：
1. 内置 `general-purpose` / `bash`
2. `config.yaml` 的 `custom_agents`
3. `config.yaml` 的 `agents` 段做**逐 agent 覆盖**（timeout / max_turns / model / skills）

> 提醒：主 Agent 是否**暴露** `task` 工具，由 `subagent_enabled` 开关控制（来自配置或运行时上下文，见第三阶段 `get_available_tools(..., subagent_enabled=...)`）。若该开关关闭，连 `task` 工具都不会出现在主 Agent 的工具列表里，多 Agent 自然不会发生。

## 十、常见坑（Pitfalls）

1. **子 Agent 无限递归** → 不会。`subagent_enabled=False` 让它拿不到 `task` 工具（`task_tool.py:239`）。✅ 设计上已防死循环。
2. **以为子 Agent 能看到主对话历史** → 不会。它只有全新的 messages（`executor.py:392`），只共享 sandbox/thread_data 文件。✅ 这正是"隔离上下文"的好处。
3. **一次想并行 10 个子 Agent** → 被 `SubagentLimitMiddleware` 截断到 ≤4 个（`subagent_limit_middleware.py`）。✅ 不要试图在 prompt 里突破。
4. **自定义子 Agent 不出现** → 检查 `subagent_enabled` 是否开启，且 `custom_agents` 的 key 名是否与 `task` 调用里的 `subagent_type` 完全一致。
5. **子 Agent 执行超时无结果** → 默认 900s；长任务要调大 `timeout_seconds`（`subagents_config.py:74`）。
6. **误给子 Agent 开放 `task`** → 即便手动写进 `tools` 白名单，`get_available_tools(subagent_enabled=False)` 也会把关（`task_tool.py:243`）。✅ 系统强制拦截。
7. **host bash 没开却用 `bash` 子 Agent** → `task_tool` 直接返回错误（`task_tool.py:187-190`）。

## 十一、本阶段小结

- DeerFlow 的"多 Agent" = 主 Agent 调 `task` 工具 → 后台起一个**独立 `create_agent` 图**的子 Agent。
- 隔离但共享文件：子 Agent 有独立消息上下文，但继承父的 `sandbox_state`/`thread_data`。
- 并发上限 [2,4]（默认 3）由 `SubagentLimitMiddleware` 硬截断；调度池 3 线程 + 超时 + max_turns 三重保护。
- 取消是协作式的（`cancel_event` 在 `astream` 边界检测）。
- 自定义子 Agent 写在 `config.yaml` 的 `subagents.custom_agents`，支持独立的 system_prompt / tools / skills / model / 超时。
